The one idea to remember

An LLM is just another dependency. It has three awkward properties.

Non-deterministic

The same input can give different output. You test distributions with evals, not exact values with asserts.

Expensive

You pay per token, with real latency. Scale, rate limits and caching are about tokens, not CPU.

Persuadable

It follows instructions, including bad ones hidden in input. That gives you a new security model.

Every section today maps back to one of these three.

This is the throughline. Come back to these three words at the end of every section. If grads remember one slide, it's this one.

1 · Where LLMOps fits

LLMOps sits inside the DevOps umbrella

DevOps CI/CD · IaC · observability · SLOs · incident response
MLOps data pipelines · training · model registry · drift monitoring
LLMOps prompts · evals · tokens · guardrails · RAG · agents · gateways

Everything you learn about DevOps still applies. LLMOps adds practices for a component you usually consume through an API instead of training yourself.

Neighbouring disciplines you'll bump into:

DevSecOps: injection, secrets FinOps: token spend Platform eng: shared LLM gateway Data eng: RAG ingestion
The big shift from MLOps: most teams don't train models any more. The work moves from training pipelines to prompts, retrieval, routing and evaluation. The model is a vendor dependency, like a database you rent.
1 · Where LLMOps fits

What carries over, and what LLMOps adds

DevOps practiceThe LLMOps version
Unit and integration testsEvals: golden datasets, LLM-as-judge, regression runs on every prompt change
Versioning codeVersioning prompt + model + parameters together. A prompt change is a deploy.
Latency and error-rate metricsPlus tokens in/out, cost per request, quality scores, refusal and hallucination rates
Deterministic outputsProbabilistic outputs, so you measure pass rates over many runs

Ask: "Which of these would your current CI pipeline catch?" Usually none of the right-hand column. A prompt edit can pass every unit test and still make answers worse. That is why evals are the test suite for LLM features.

2 · Production concerns · Scale

At scale, the unit is the token

Throughput

Providers limit TPM (tokens per minute) and RPM (requests per minute). You hit the token limit long before your servers sweat.

Latency

Track time to first token and total time. Stream responses to users. Send non-interactive work to batch APIs, which are often about half price.

Capacity

Queue and apply backpressure. Set context-window budgets per feature. Consider provisioned throughput for steady high volume.

Back-of-envelope sizing

1,000 users × 20 requests/day × 3,000 tokens = 60M tokens/day ≈ 42k tokens/min on average

Traffic isn't flat. Plan for peaks of 3–5× the average, so ask for quota of about 150–200k TPM.

Walk through the arithmetic live. 60 million divided by 1,440 minutes is about 41,700. Ask what happens at 9am Monday. RAG prompts are often 3–8k tokens because of the retrieved context, so they dominate the bill.

2 · Production concerns · Guardrails

Guardrails check both sides of the call

Input guardrails

  • PII detection and redaction before text leaves your network
  • Prompt-injection and jailbreak classifiers
  • Topic and policy filters ("this bot only answers billing questions")
  • Size limits on input and attachments

Output guardrails

  • Schema validation with structured outputs, plus retry on failure
  • Toxicity and safety checks
  • Grounding checks: is the answer supported by the retrieved context?
  • Escaping before rendering, never raw HTML

Tooling: provider moderation endpoints, Guardrails AI, NVIDIA NeMo Guardrails, Bedrock Guardrails, Azure AI Content Safety.

Every guardrail costs latency and money, and it has a false-positive rate. Treat each one like an alert rule: measure it and tune it.
Point out that a guardrail that is another LLM call doubles your latency on that path. Cheap classifiers go first; expensive LLM judges only run where the risk is high.
2 · Production concerns · Rate limiting

Rate limiting runs in two directions

Your userstenants, API keys, agents
→
Your quotastoken bucket per user and tenant, daily spend caps
→
Your appthe gateway
→
Provider limitsHTTP 429, retry-after, TPM/RPM
→
Providerthe model API

Protect yourself from users

Limit on tokens, not just requests: one request can be 50 tokens or 150,000. Add budget alerts and hard spend caps (LLM10).

Respect the provider

Honour retry-after. Retry with exponential backoff and jitter so clients don't all retry at once.

delay = min(cap, base * 2**attempt)
delay = delay * random.uniform(0.5, 1.0)  # jitter
An agent stuck in a loop is the classic cost incident: one user, thousands of calls, overnight. Per-user token quotas plus per-agent step limits stop it.
2 · Production concerns · Multi-deployment

Deploy prompts and models like you deploy code

Availability

Use multiple regions or providers so you can fail over during an outage. Keep evals for each fallback model, because fallback answers will differ.

Routing

Send easy requests to a small, cheap model and escalate hard ones to a large model. Route by task type, tenant tier or a classifier.

Safe rollout

Use shadow traffic (run the new prompt and compare offline), then a canary at 5%, then full rollout. Roll back on eval scores, not just on errors.

Version pinning

Pin exact model versions, not "latest". Track deprecation dates like certificate expiries. Data residency can decide which regions you are allowed to use.

Story: a provider silently improved a model alias and a JSON-extraction feature started adding commentary. Pinning plus a nightly eval run would have caught it.
2 · Production concerns · Caching

Three kinds of cache, three different risks

CacheKeyed onWinWatch out for
Exact matchHash of prompt + model + paramsFree repeat answersLow hit rate on free text. Never share entries across tenants.
SemanticEmbedding similarity to past questionsHits on paraphrases"Similar" is not "same": cancel my order vs cancel my account. Tune the threshold with evals.
Prompt / prefix (provider side)A long, stable prefix such as the system prompt, tools or documentsLarge cost and latency cuts on the cached partOnly works if the prefix is byte-identical. Put stable content first and variable content last.

Prefix caching is usually the biggest and safest win, because the model still generates a fresh answer.

A common mistake: putting a timestamp or user name at the top of the system prompt, which breaks the prefix cache on every request. Order your prompt from most stable to least stable.

3 · RAG · Chunking

Chunking decides what can be found

Strategies

  • Fixed size + overlap: simple, but cuts through tables and sentences
  • Recursive / structure-aware: split on headings, paragraphs and code blocks first
  • Semantic: split where the topic changes, measured by embedding distance
  • Parent–child: retrieve small chunks, send the larger parent section to the model

The trade-off

Small chunks match precisely but lose context. Large chunks carry context but dilute the match and cost more tokens.

A common starting point is 300–800 tokens with 10–20% overlap. Then tune it with retrieval evals.

Attach metadata to every chunk: source, section, date, version, access-control list. You need it for filters, citations and deletes.

There's no universally right chunk size. It depends on the documents. Policies want section-sized chunks; FAQs want one Q&A per chunk; code wants function-level chunks.

3 · RAG · What a vector search does

Retrieval finds the nearest neighbours of the question

Stress that the embedding model for queries and documents must be the same version. Switch models and the query lands in a different space, which is why changing embedding models means re-indexing.
3 · RAG · Embeddings

Vector size is a storage and latency bill

Dimensionsfloat32int8binary
3841.5 GB384 MB48 MB
7683.1 GB768 MB96 MB
1,5366.1 GB1.5 GB192 MB
3,07212.3 GB3.1 GB384 MB

Raw vectors for 1 million chunks. The index structure (such as an HNSW graph) adds more on top.

  • More dimensions can improve recall, but cost memory, storage and query time.
  • Matryoshka embeddings let you truncate to fewer dimensions with a small quality loss.
  • Quantisation (int8, binary) cuts memory 4–32×. Re-score the top results with full vectors.
  • Use the distance metric the model was trained for: cosine, dot product or L2.
  • Changing the embedding model means re-embedding everything. Version the index like a database schema and migrate with a dual-write.
Do the maths once: 1,536 dimensions × 4 bytes is about 6 KB per vector, times a million is about 6 GB. That has to sit in RAM for HNSW. That's why quantisation matters at scale.
3 · RAG · Vector stores

Running the vector store

Options

pgvector (Postgres), OpenSearch / Elasticsearch, Qdrant, Weaviate, Pinecone, Milvus, plus managed cloud options.

If you already run Postgres, pgvector is often enough to start.

Index types

HNSW: fast and accurate, memory-hungry.

IVF / IVF-PQ: compressed, cheaper, lower recall.

All are approximate (ANN). Tune parameters such as ef_search to trade recall for latency.

Day-2 ops

  • Backups and restore tests
  • Incremental re-ingestion and freshness SLAs
  • Deletes: right-to-be-forgotten must reach the index
  • Sharding and multi-tenancy isolation
Deletes are the one people forget. If a document is removed from the wiki but its chunks stay in the index, the bot keeps quoting it. Build deletion into the ingestion pipeline from day one.
3 · RAG · Retrieval

Hybrid search beats either method alone

Keyword (BM25)

Great for exact terms: error codes, product names, IDs like ERR_4012.

Dense vectors

Great for meaning: "can't log in" matches "authentication failure".

Combine them with Reciprocal Rank Fusion

RRF(doc) = Σ 1 / (k + ranki(doc)) with k ≈ 60

It uses ranks only, so you don't have to normalise scores from two very different systems.

  • Query rewriting: clean up or expand the user's question, or generate several queries
  • HyDE: generate a hypothetical answer and search with that
  • Metadata filters: product, date, and the user's permissions, applied in the query
  • top-k: retrieve wide (around 50), then let the re-ranker narrow it down
Quick example of RRF: a doc ranked 1st by BM25 and 3rd by vectors scores 1/61 + 1/63. Ranked 2nd by both, it scores 1/62 + 1/62. Being consistently good beats being great in one list.
3 · RAG · Hybrid search, worked

Reciprocal Rank Fusion rewards being good in both lists

Work one row aloud: the runbook is rank 1 in BM25, so 1 over 61, and rank 2 in vectors, so 1 over 62. Add them up. Ranks only, no score normalisation needed.
3 · RAG · Re-ranking

Retrieve cheaply, then re-rank carefully

Bi-encoder (retrieval)

Query and document are embedded separately. Document vectors are precomputed, so search over millions is fast. But the model never sees query and document together.

Cross-encoder (re-ranking)

Query and document go into the model together and get one relevance score. Much more accurate, but too slow to run over the whole corpus.

1,000,000 chunksin the index
→
Top 50hybrid retrieval · ~20–50 ms
→
Top 5cross-encoder · ~50–200 ms
→
Promptfewer, better tokens

Options: Cohere Rerank, bge-reranker, Jina, ColBERT (late interaction, in between). MMR removes near-duplicates for diversity. An LLM can re-rank too, at a much higher cost. Latency figures are typical ranges, so measure your own.

Re-ranking often improves answer quality more than switching to a bigger LLM, and it reduces prompt tokens because you send 5 good chunks instead of 20 mediocre ones.

3 · RAG · Security and evaluation

Secure it, then measure each half separately

Security

  • Retrieved documents are untrusted input. A wiki page can contain an injected instruction (LLM01).
  • Enforce access control at retrieval time with metadata filters. Never rely on the prompt to hide data (LLM08).
  • Watch for poisoned documents entering the index (LLM04).

Evaluation

Retrieval: recall@k, MRR, nDCG. Did the right chunk come back, and how high?

Generation: faithfulness (groundedness), answer relevance, context precision.

Frameworks: RAGAS, DeepEval, TruLens. Build a golden set of 50–200 real questions with known source chunks.

Score retrieval and generation separately so you know which half broke.
If recall@5 is low, fix chunking, embeddings or the re-ranker. If recall is high but faithfulness is low, fix the prompt or model. Without the split you'd be guessing.
4 · Workflows vs agents

Who decides the next step: your code or the model?

Workflow

LLM calls arranged in code paths you defined. The steps are known in advance.

prompt chainingroutingparallelisationorchestrator–workersevaluator–optimizer

Agent

The model decides its own steps in a loop: think, call a tool, read the result, repeat until done.

while not done and steps < max_steps:
    action = llm(goal, history, tools)
    result = run(action)
    history.append(result)
Start with the simplest thing that works. Use a workflow when you know the steps. Use an agent only when you can't.

Framing from Anthropic's "Building effective agents".

Many things sold as "agents" are workflows, and that's a good thing. Workflows are cheaper, faster and easier to test. Agents earn their cost on open-ended tasks.
4 · Workflows vs agents · Patterns

Four workflow shapes you'll build again and again

Prompt chaining

Fixed steps. A cheap check between calls catches errors before they compound.

Routing

One cheap classification decides which model or prompt handles the request.

Parallelisation

Split the work, or run the same prompt several times and vote. Cuts latency.

Evaluator–optimizer

Loop until a second model, or a rule, says the output is good enough. Cap the loops.

Every arrow here is written in code, which is what makes these workflows. Point at the gate in prompt chaining and the evaluator loop: those are where evals live in production. The capstone router is the routing pattern.

5 · Code mode vs MCP

MCP: one standard plug for tools and data

Host appchat app, IDE, your agent
↔
MCP clientone per server connection
↔
MCP serversGitHub · Jira · Postgres · your internal API

How classic tool calling works

  • Every tool's name, description and JSON schema is loaded into the context
  • The model calls one tool, and the full result comes back into the context
  • Repeat for each step

Why teams like it

  • Write a server once and use it from any MCP-capable client
  • Simple, auditable, one call at a time
  • Good fit for a handful of tools and small results

Spec: modelcontextprotocol.io

Analogy: MCP is to LLM tools what USB is to peripherals. The cost: with 40 tools across 8 servers, the definitions alone can take tens of thousands of tokens before the user has typed anything.
5 · Code mode vs MCP

Code mode: the model writes code that calls the tools

// runs in a sandbox, not in the model's context
const accounts = await crm.listAccounts({ updatedSince: "2026-11-01" });
const invoices = await billing.listInvoices({ month: "2026-11" });
const billed = new Set(invoices.map(i => i.accountId));
const missing = accounts.filter(a => !billed.has(a.id));
console.log(missing.length, missing.slice(0, 20));

Tools are exposed as a code API, often generated from MCP servers. The model writes a script, it runs in a sandbox, and only the printed result returns to the model.

  • Loads tool definitions only when needed
  • Thousands of intermediate rows never enter the context
  • Loops, filters and joins happen in one step instead of dozens of calls

Popularised in 2025 by Cloudflare ("Code Mode") and Anthropic ("Code execution with MCP"), which reported one example dropping from about 150k to about 2k tokens.

Models have seen far more real code than tool-calling transcripts, so they're good at it. The ops cost is that you now run an untrusted-code sandbox in production.
5 · Code mode vs MCP

They're layers, not rivals

ConcernDirect MCP tool callsCode mode over MCP
Token costGrows with tool count and result sizeMostly flat, because only results return
LatencyOne model round-trip per callOne script, many calls
InfrastructureMCP servers onlyMCP servers plus a hardened code sandbox
AuditabilityEach call is visibleNeed to log the generated code and its calls
SecurityPer-tool permissionsSandbox escape and egress risk; same tool permissions still apply

The LLMOps job either way

  • Govern MCP servers: an approved allow-list, pinned versions, review of third-party servers (supply chain, LLM03)
  • Auth: scoped, per-user credentials, not one shared admin token
  • Run the sandbox like production: resource limits, no default egress, patched images
Code mode usually sits on top of MCP. MCP describes the tools; code mode changes how the model uses them. Choose per use case.

6 · Capstone · Azure AI Foundry

Keep the Foundry deployments busy without dropping requests

Your team's Foundry project serves one assistant. You can deploy a small model, a general model and a large reasoning model. Queries arrive at about 400 a minute, with peaks 1.5× higher.

Provisioned (PTU)

Reserved throughput billed by the hour, used or not. Idle PTU is wasted money. Azure Monitor shows its utilisation, and above 100% the deployment returns 429.

Standard (pay-as-you-go)

Billed per token, limited by a TPM quota. Azure grants 6 RPM for every 1,000 TPM. Good for spiky or overflow traffic.

Spillover

Run PTU hot and send overflow to a Standard deployment. Do it with an API Management backend pool using priorities, or with Foundry's spillover setting.

Goal: provisioned deployments at 95%+ average utilisation, under 1% of requests throttled at peak, and at least 90% of complex queries answered by the reasoning model.

Simulator rules: simple queries use 1,200 tokens, medium 2,500, complex 3,000. The reasoning model uses 2.5× tokens on anything it handles, because of hidden reasoning tokens. All numbers are illustrative.

Set up the scenario before handing over. The tension: PTU is cheapest when full, but full PTU means peaks overflow. The answer combines the gateway, router, cache and a queue. Let people predict what they'll need before they touch the simulator.

  • APIM AI gateway policies: llm-token-limit, llm-semantic-cache-lookup / -store, backend pools with priorities and circuit breaker

Tie back to the three properties: expensive (PTU utilisation and spillover cost), non-deterministic (router accuracy changes quality), persuadable (the gateway is also where token limits stop abuse).

Three properties, and the practices they demand

Non-deterministic

Evals as your test suite. Version prompt + model together. Canary on quality. Score RAG retrieval and generation separately.

Expensive

Token-based quotas and budgets. Prefix caching. Model routing. Re-rank to send fewer, better tokens. Code mode for heavy tool use.

Persuadable

OWASP LLM Top 10. Guardrails on both sides. Access control at retrieval. Least-privilege tools, approvals and sandboxes for agents.
